# QL-429 — Protected External Anchor Enrollment, Original-Host Fresh Challenge Orchestration & Independent Three-Master Pilot Re-entry Witness

## Implemented boundaries

QL-429 introduces a protected **public-key trust enrollment** workflow, an **unpredictable one-use challenge** generated only after QL-428's signed external-anchor readback and durable supervised owner precheck, and an original-host OFF response independently countersigned by the three Masters and dual owner/reviewer. Protected Node-only implementation is in runtimes/master-telemetry/ql429-anchor-enrollment-challenge.mjs.

This release does **not** configure an external anchor service, enroll actual signer devices, sign anything with production private keys, trigger a Windows task, start or enable a receiver, install a live scheduler, prove CONNECTED or make any runtime-uptime claim. Real original-host and off-host connections remain deployment work with original-owner supervision. All success outputs explicitly keep receiver OFF, connection HOLD, slave gate HOLD.

## Supervised original-host procedure

1. Independently verify the separately administered off-host external anchor store identity, its Ed25519 anchor and readback signers, the original Windows host DESKTOP-AE894KC, and all three Master Ed25519 signer public keys. Private signing keys remain on their original devices. Source and controller 40-hex revision identities must be exact for the pilot.
2. Use openQl429ProtectedEnrollmentLedger with an **absolute, private, durable** protected backend directory. Sign the exact external enrollment public-pin record with **two distinct owner/reviewer keys** and independent key possession proofs from off-host anchor signer, off-host reader signer and original Windows host signer, all bound to the enrollment digest. EnrollQl429ExternalAnchor commits a single immutable verified public enrollment after independent physical and cryptographic checks. This is not an automatic external service setup.
3. Reopen the authenticated QL-426/QL-427 chains, QL-428 durable supervised precheck store and original host's acceptance. issueQl429OriginalHostChallenge independently rechecks the off-host QL-428 signed anchor and fresh readback using the **enrolled pins**. It issues a **cryptographically random 192-bit one-use challenge ID**, bound to the old incident, exact scope and revisions, the external anchor digest and QL-428 durable precheck digest, with a 60-second expiry. No browser flag or old challenge is sufficient.
4. The actual original Ree Windows host obtains the challenge through a protected human-supervised path. Its separately enrolled private host key must sign an exact QL-429 response binding challenge digest, challenge ID, original source/incident/re-entry and a **fresh signed receiver OFF state**. The proposed next ceremony ID must differ from the old one. verifyQl429OriginalHostChallenge rejects forged, replayed, wrong-device, ON, wrong-episode, expired or non-monotonic responses.
5. The three distinct Masters—Rosevear AI Hub, Rosevear Comms Hub, AI Data Platform—must each independently sign fresh QL-429 pilot re-entry witness reports for that **exact host response and proposed new ceremony**, with status WITNESSED_NEW_SUPERVISED_PILOT_PRECHECK_ONLY. Then two distinct owner/reviewer identities separately sign the exact ordered three-Master digest, with action ACCEPT_SIGNED_PRECHECK_ONLY_REQUIRE_NEW_QL424_CEREMONY_KEEP_OFF.
6. acceptQl429ThreeMasterPilotWitness validates all six signatures, records **one immutable, fsynced witness receipt**, and **returns connection HOLD, receiver OFF verified at that signed snapshot, slave gate HOLD**. The witness is a precondition only; real one-TEST reactivation requires **a NEW independent QL-424 supervised original-host ceremony**, fresh owner authority, protected execution and independent live receiver proof.
7. Export independent immutable copies of enrollment/challenge/witness digests to a separate audit custodian. An admin with full access to the local ledger may delete files; local hash consistency alone does not protect against privileged deletion. The code does not implement a remote immutable store, Windows signing transport or autonomous session orchestrator.
