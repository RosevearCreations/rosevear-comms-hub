# QL-354 — Owner-supervised original credential custody, signed enrollment intake and first genuine TEST challenge

## What this build actually delivers

QL-354 adds an exact **offline, signed-intake verifier**, a two-PC Windows owner handoff, a **server-only** one-shot original enrollment transaction gated by two owner Ed25519 signatures **plus independently authenticated issuer and field-witness verifiers**, and a fresh, **unsigned** one-device TEST challenge tied to the original enrollment. Its signed challenge receipt reconciliation requires the original device Ed25519 signature **and an immutable private PostgreSQL receipt**. Tests cover wrong signer, changed witness bytes, roles, expiry, replay, no prior receipt and six HELD peers.

QL-354 **does not** manufacture original owner decisions, original issuer authentication, independent field witnessing, an original Windows device private signature, a receiver database login, or a live six-app connection. The production CI cannot contact Ree's PC or Jack's laptop. As of the independent 2026-11-06 live SQL readback, the enrollment and receipt tables each contain **zero** rows, and `ql340c_private_receiver` remains **NOLOGIN**. No live database writes or owner credentials were performed by this build. `main` GREEN indicates software release checks only.

### 2. Independent original issuer and field evidence review

Ree and Jack each separately inspect the *original* four Windows process, TLS certificate/chain, Tailnet ACL, and rollback witness **bytes**, and the source/master/device public candidate fingerprints. ### 6. Separate database enrollment and least-privilege secret custody

An independently authenticated original issuer and field witness must verify **the exact same signed enrollment SHA-256** in the *private* review service. QL-354's server-only `authorizeQl354IndependentIntake` refuses fake/serialized proof objects and returns an unexportable, single-use permit only after both external verifiers succeed. `insertQl354OriginalEnrollmentOnce` uses a separately approved administrator transaction, checks for zero existing enrollments, zero revocations, zero receipts and all six HELD peers, then performs **one parameterized, append-only, original-device `REVIEWED_TEST` enrollment**. It cannot insert with `anon`, `authenticated` or the receiver role. The admin transaction must never run inside a browser or on Ree's Windows receiver; do not share the administrator password. This function has **not** executed in production.

Only after independent authorization and a legitimate administrator-controlled credential provisioning decision can the private Windows role be enabled. The current `ql340c_private_receiver` is `NOLOGIN`; no password can authenticate as it until an independently authorized administrator provisions it. It rejects a `postgres`/service-role URL. Do not run it until the specific credential exists. No automatic credential, role LOGIN change, or database mutation was performed here.

### 7. Exactly one original-device TEST challenge — still no six-app connectivity

After real enrollment and private reader authentication, `prepareQl354OneDeviceChallenge` queries `current_user` and refuses anything except the limited `ql340c_private_receiver`. `reconcileQl354SignedChallenge` then checks the original signed envelope, exact enrolled device public key, dedicated receiver identity and **one real immutable PostgreSQL receipt**. A successful receipt remains `DISCONNECTED / HOLD` for all six source applications. Independent app-level owner consent and signed handshakes come next. Stop only the *precise* supervised process when completing rollback; preserve LAN Caddy and existing AI Hub startup tasks.

- There is **no** unattended installer, database login provisioner, public origin route, test packet device signer, Tailnet firewall change or customer communication in QL-354.
